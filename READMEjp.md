# simple-system-builder

ChatGPTのWeb-UIだけでシステム開発を完結させるためのSkill — Chatが司令塔、GitHubが正本。

[English](README.md) | 日本語

**解説記事:** [ChatGPTとGitHubで、Web UIだけでシステムを作るためのSkill](https://note.com/norito_hiraoka/n/n50d293161d97)

## これは何か

IDEを開かず、ターミナルも開かず、ChatGPTのChat画面から出ないまま、要求整理から設計・実装・テスト・CI・デプロイまで進めるためのSkillです。

ただし、このSkillの正体は「コード生成マクロ」ではありません。**どのような考え方でシステムを作り、どこまで自分で進み、どこで人間に判断を戻すか**を定めた、AI開発者の行動規範です。

中心にあるのは三つの原則です。

1. **最小十分。** 目的を満たす最も単純な仕組みを選ぶ。一つのDBで済むなら増やさない。マイクロサービスが不要ならモノリスでよい。単純さ自体が目的ではなく、シンプルで、なおかつ目的を十分満たしていること。
2. **複雑さは隔離する。** 現場独自の帳票やcomputer useなど、どうしても複雑になる部分は、なくすのではなく居場所を限定する。adapterの向こう側に閉じ込め、業務ロジックの中心に持ち込ませない。
3. **未来は作り込まず、変更できる余地だけ残す。** 将来の機能を先に作らない。将来変更しそうな場所に安い継ぎ目（設定値・環境変数・テンプレート・adapter・Migration）だけを置く。

一番守りたいのは開発速度ではなく、**AIに開発させてもシステムを複雑にしないこと**です。

## なぜ成立するのか

このSkillが機能するのは、次の技術が組み合わさったことによります。

### 頭脳

- LLMの言語理解力と設計力が上がったこと。実装力・検証力も上がったこと。
- ハーネスやコントラクトなど、実装を制御する能力も上がったこと。

### 回路

- MCP経由で、ChatGPTがGitHubとやり取りできるようになったこと。

### 土台

- GitHubには文書もシステムも置けること。GitHub Actionsを使えば自動実行も可能なこと。
- GitHubのこの性質自体は以前からあるが、LLMが読み書きの主体になったことで、AIの外部記憶と実行装置という意味を持つようになった。

### 出口

- 実際のシステムのデプロイ先は、ローカル環境でもクラウド環境でも選べるようになっていること。
- LLMが環境設定のガイドを務め、実際の設定作業も担えること。

どれか一つ欠けても成立しません。

## 役割分担

```text
Chat   = 指示と判断の場所
GitHub = 開発成果と状態の記録場所（正本）
```

要求・要件、アーキテクチャ、データモデル、UX、コード、プロンプト、テスト、GitHub Actions、デプロイ設定、重要な設計判断は、すべてGitHubに置きます。Chatには状態を持たせません。会話がどれだけ長くなっても、スレッドを跨いでも、開発の現在地はリポジトリから復元できます。

## リポジトリ構成

```text
simple-system-builder/
├── SKILL.md                 # Skill本体（行動規範と進行方法）
├── references/              # 運用規則
│   ├── principles.md            # 設計原則
│   ├── complexity-boundaries.md # 複雑さの隔離
│   ├── prototype-enterprise.md  # プロトタイプと将来変更の継ぎ目
│   ├── repository-contract.md   # リポジトリの構成規約
│   ├── tooling.md               # GitHub・クラウド・実行ツールの扱い
│   └── workflow.md              # 進行手順
├── agents/                  # エージェント設定
├── scripts/                 # scaffold / 状態更新 / 検証スクリプト
└── assets/project-template/ # 生成されるプロジェクトの雛形
```

## 導入

1. このリポジトリ一式をzip化し、ChatGPTにSkillとして登録します。
2. ChatGPT側でGitHubコネクタ（またはGitHub MCP）を接続します。

## 初回セットアップ

開発対象のリポジトリについて、次の二つは**手動で**行います。

- リポジトリの作成
- ChatGPTのコネクタへの、そのリポジトリに対する書き込み許可の設定

これは機能不足の回避策ではありません。Skill自身が「権限に関わる判断は人へ戻す」と定めているため、権限の付与は自動化しない設計です（`references/tooling.md` の「初回セットアップ」参照）。一度だけ人間が鍵を開け、あとはChatの画面から出ずに開発が進みます。

## 使い方

Skillは最初から動かしません。

1. 要求整理・要件定義・技術的な成立性の検討までは、通常のChatで人とAIが一緒に考えます。
2. 「だいたい作るものが見えた。これを実際のシステムにしよう」となった時点でSkillを発動します。ここが探索から構築への境界です。
3. 発動後は、GitHubへ開発状態を移し、原則として自動で進みます。

```text
通常のChat
  要求整理 → 要件定義 → 技術的検討 → 「これを作る」と判断
━━━━━━━━━━━━━━━━━━
        Skill発動
━━━━━━━━━━━━━━━━━━
  GitHubへ開発状態を移す
     ↓
  Data ⇄ UX
     ↓
  Infrastructure ⇄ Permission
     ↓
  最小十分アーキテクチャ確定
     ↓
  設計 → 実装 → テスト → GitHub Actions → デプロイ
     ↓
  原則として自動継続
```

### 人に戻す判断

基本方針は「方法はSkillに任せる。目的に関わることだけ人が判断する」です。人に戻すのは、要求そのものが変わるとき、UXやデータの意味を決めるとき、権限やセキュリティに関わるとき、高額な費用が発生するとき、簡単に戻せない変更をするときです。

また、**Data ⇄ UX**と**Infrastructure ⇄ Permission**の二つの領域は、一方向に決められないため、Skillが決め切らずユーザーと往復します。
