# GitHub・クラウド・実行ツールの扱い

## GitHub

GitHub操作には、利用可能なApp、connector、MCP、または認証済みCLIを使う。変更操作の前にツールがその操作を正式に提供しているか確認する。

優先順位:

1. 接続済みのGitHub Appまたはconnector
2. ユーザーが指定したGitHub MCP
3. 認証済みのGitHub CLI
4. ローカルGitリポジトリを作り、pushだけを手動操作として残す

公開指定がなければ新規リポジトリをprivateにする。既存リポジトリでは設定を勝手に変更しない。

## 初回セットアップ（発動時チェック）

Skill発動直後、実装に入る前に、対象リポジトリへ実際に書き込めるかを確認する。

1. 接続済みツールで対象リポジトリの読み取りと書き込み権限を確認する。
2. リポジトリが存在しない、または書き込みできない場合、ローカル生成へ切り替える前に、次をユーザーへ案内する。
   - リポジトリを手動で作成する手順（リポジトリ名の案とprivate設定を含む）
   - ChatGPT側のGitHubコネクタに、そのリポジトリへの書き込み許可を与える手順
   - 設定が済んだら知らせてもらい、書き込み確認をやり直すこと
3. 案内後も書き込みできない場合に限り、ローカルにGitHub-ready構成を作り、必要な手動操作を一つにまとめて示す方式へ切り替える。切り替えたことを明示し、黙って迂回しない。

リポジトリ作成と権限付与は自動化しない。権限に関わる判断を人へ戻す方針に従うものであり、機能不足の回避策ではない。

## GitHub Actions

現在の技術スタックに必要な最小ワークフローだけを作る。

- install
- lintまたは静的検査
- test
- build
- 必要な場合だけstaging deployとsmoke test

同じ処理を複数workflowへ複製しない。キャッシュ、matrix、複雑な再利用workflowは、時間や複数環境の要件が確認できてから追加する。

失敗時はActionログを読み、再現可能ならローカルで再現し、修正、再実行、状態更新まで進める。

## クラウド

- ユーザーが使うクラウドまたは既存基盤を優先する。
- 認証済みconnectorまたはCLIがある場合だけ実操作する。
- 最小権限を使う。
- 長期Secretより、利用可能ならOIDCなど短期認証を優先する。
- 強い権限、本番Secret、公開範囲の拡大は人へ戻す。
- stagingは承認済み範囲で自動化し、本番はプロジェクト方針に従う。

## ローカルPC

- OSと既存ツールに合う最小の実行方法を選ぶ。
- 不要な仮想化やコンテナを追加しない。
- 再現性が必要でコンテナが有効な場合だけ採用する。
- 管理者権限が必要な操作は理由と影響を示す。
- 起動、停止、初期化、テストを短いコマンドへまとめる。

## Secretと機密情報

- Secretをリポジトリ、生成文書、ログ、Issueへ書かない。
- `.env.example` にはキー名と説明だけを置く。
- 実値はGitHub Secrets、クラウドSecret管理、OSの安全な保管先を使う。
- ログへ個人情報や認証情報を出さない。

## できない操作

接続、認証、権限、ツール機能が不足している場合は、実行済みとして扱わない。準備可能な作業を完了し、ユーザーに必要な操作を一つにまとめて示す。
