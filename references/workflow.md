# 開発ワークフロー

## 1. 構築開始を判定する

会話から目的、利用者、主要ユースケース、受入条件、制約、技術的成立性を抽出する。

- 目的と技術的成立性が見えている場合は開始する。
- 小さな不足は仮定として記録し、開始する。
- 目的や主要業務フローが複数解釈できる場合は、質問をまとめて通常のChatへ戻す。

## 2. GitHubを正本にする

既存リポジトリを優先する。新規の場合はGitHubの利用可能な書き込み手段を確認する。

- リポジトリ作成が可能なら、非公開を初期値として作る。
- 作成できない場合はローカルにGitHub-readyな構成を作る。
- 実行できないGitHub操作を実行済みとして扱わない。
- `scripts/scaffold_project.py` で最小文書と状態管理を作る。

## 3. 基準線を共同で固める

### Data–UX基準線

利用者の行動、必要な情報、データの意味、状態遷移、表示・入力・取消・エラーを往復して整合させる。

次を満たせば実装へ進む。

- 主要な利用経路が通る。
- データの意味を業務用語で説明できる。
- 誰が何を見て操作するかが分かる。
- エラー、取消、再実行の扱いが分かる。

### Infrastructure–Permission基準線

クラウドまたはローカル実行環境、実行主体、必要リソース、最小権限、Secret、ログ閲覧、デプロイ認証を整合させる。

強い権限、本番Secret、本番データアクセス、公開範囲の拡大は人へ戻す。

## 4. 最小の縦切りで実装する

最初に一つの受入条件を端から端まで通す。

1. 入力または利用操作を用意する。
2. 業務処理を実装する。
3. 永続化または外部境界を接続する。
4. 出力または利用結果を確認する。
5. 自動テストを作る。
6. ローカルまたはstagingで実行する。

骨組み全体を先に作り込まず、動く一経路を作ってから広げる。

## 5. 自動ループを回す

各受入条件について次を繰り返す。

1. 実装する。
2. テストする。
3. CIを実行する。
4. ログを確認する。
5. 修正する。
6. 文書と状態を更新する。
7. 次へ進む。

軽微な設計変更、リファクタリング、テスト追加、CI修正、staging再デプロイは止めずに進める。

## 6. 人へ戻す条件

次の場合だけ停止する。

- 目的または主要要件の変更が必要である。
- 業務上の意味が一意に決まらない。
- 権限、公開範囲、個人情報、費用、契約へ影響する。
- 本番データを破壊する可能性がある。
- 単純な構成では重要要件を満たせない。
- 安全に検証できず、推奨案へ十分な確信を持てない。

判断依頼は次の形にする。

```text
何が決まらないか:
目的への影響:
単純さへの影響:
推奨案:
他の選択肢:
人が行う必要のある操作:
```

質問を細切れにしない。判断待ちでも独立した作業は継続する。

## 7. 完了を確認する

- 主要受入条件が実行環境で確認できる。
- テストとCIが通る。
- デプロイと復旧の手順が短く説明できる。
- 文書と実装が一致する。
- 不可避の複雑さが境界へ隔離される。
- 将来のエンタープライズ化は、未実装の機能ではなく移行経路として残る。
