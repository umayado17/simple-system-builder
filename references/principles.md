# 最小十分アーキテクチャ原則

## 判断の順序

1. 目的と受入条件を言い直す。
2. 一番小さい構成で達成する案を作る。
3. 達成できない要件だけを特定する。
4. その要件を満たす最小の技術を追加する。
5. 追加後に、削れる構成がないか再確認する。

## 優先順位

次の順で優先する。

1. 利用者の目的を満たす。
2. 正しく安全に動く。
3. 理解、修正、運用が容易である。
4. 変更しやすい。
5. 性能や規模に十分対応する。
6. 技術的な新しさや一般論に合う。

下位の理由だけで上位を犠牲にしない。

## 初期値

特別な理由がなければ、次を初期値にする。

- 一つのデプロイ単位
- 一つの主要データストア
- 一つの主要実行経路
- 少数の外部サービス
- 実績があり、チームが理解しやすい技術
- 短い起動、テスト、デプロイ手順

## 複雑さの予算

各コンポーネントに現在の要件上の役割を持たせる。次のいずれにも答えられないものを入れない。

- どの受入条件を満たすためか。
- 除いた場合に何が破綻するか。
- 運用者が障害時にどう確認し、戻すか。
- より単純な代替をなぜ採用できないか。

## 複雑さを追加する前の確認

- 既存モジュールの追加機能で済まないか。
- 設定、テンプレート、アダプターで隔離できないか。
- 現在の負荷や利用者数で本当に必要か。
- 問題を計測してから追加できないか。
- 将来の可能性ではなく、現在の証拠があるか。

## 単純さのレビュー

主要設計の確定前と大きな変更後に、次を短く答える。

- この構成の最小単位は何か。
- 削除できるサービス、DB、キュー、抽象化はあるか。
- 不可避の複雑さはどこに閉じ込めたか。
- もっとも壊れやすい境界はどこか。
- 将来の変更に備えて置いた継ぎ目は何か。
- その継ぎ目は現在の実装をどれだけ複雑にしたか。

最後に `docs/architecture.md` へ「なぜ最小十分か」を一段落で残す。

## 禁止する考え方

- 将来必要になるかもしれないため、現在使わない基盤を実装する。
- 一般的なベストプラクティスだからという理由だけで分割する。
- 高度な技術を使うこと自体を品質とみなす。
- 運用方法を決めずにコンポーネントを増やす。
- 抽象化の対象と変更理由を示さず、汎用フレームワークを作る。
